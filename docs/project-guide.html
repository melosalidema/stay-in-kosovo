Project Guide

How Stay in Kosovo is built

A complete walkthrough of the platform: what each layer does, how a request travels from a tap on a phone to PostgreSQL and back, how the recommendation, pulse, itinerary and mobility engines work, and how every piece is wired to the next. Read it top to bottom, or jump in from the sidebar.

1. What this project is

One Next.js application that contains the whole product — screens, API, business logic and data access.

Stay in Kosovo is a tourism and local-discovery platform for Kosovo. It is not a listing site with a search box bolted on. It is built around one idea: a place is worth recommending because of how it fits the moment you are in — the mood you are in, how far you will travel, what you can spend, what time it is, and what is actually happening nearby right now.

That idea is implemented as a set of small, deterministic engines sharing one data model. Every meaningful action — a view, a save, a check-in, a route request, a review — is recorded and fed back into those engines, so the product gets more useful the more it is used.

Who uses it

Traveller / local

Browses by mood, filters by budget and travel, saves places, generates a day plan, compares transport options, and leaves reviews.

Business owner

Submits a place for review, manages events and photos, and sees how people find and save them.

Administrator

Approves submissions, moderates reported reviews, and verifies locations.

The system itself

Continuously re-ranks places, recalculates city activity, and re-prices travel options from the interaction stream.

What makes the architecture distinctive

The single most important decision is that the app works with no database and no third-party API keys. A full Kosovo dataset ships in the repository, every engine has a deterministic path, and every external call has a fallback. The database and integrations are an upgrade, not a prerequisite. This is covered in detail in section 15.

4. Architecture layers

Five layers, each with one job. Nothing skips a layer.

The rule that keeps the codebase readable is that a layer may only talk to the layer directly below it. A page never queries the database. A service never renders markup. An API route never contains business logic.

Why the boundary sits where it does

  • Pages may call services directly. A Server Component rendering the homepage calls getHomepageMapPlaces() during render. Going through HTTP would add a hop and lose typing for no benefit.
  • Client Components cannot. A browser cannot run pulse-engine.ts, so anything interactive goes through a route handler. That is the entire reason the API exists.
  • Services are pure where it matters. The recommendation, pulse, itinerary and mobility engines take plain input objects and return plain output objects. No request, no database, no framework. That is what makes them testable in milliseconds.

5. Request lifecycle

Three concrete journeys through every layer.

A. Opening the homepage (server-rendered)

1 · Middleware

src/middleware.ts runs first on every request. It generates a nonce, attaches security headers (CSP, HSTS, X-Frame-Options), and checks whether the path is role-protected. / is public, so it passes straight through.

2 · Render

src/app/page.tsx is an async Server Component. It awaits getHomepageMapPlaces() from location-layer.ts before producing any markup.

3 · Data probe

location-layer asks isDatabaseReachable(), which opens a TCP socket to DATABASE_URL with a 250 ms budget. The answer is cached for 60 s when reachable and 10 s when not, so a down database costs one probe rather than one per request.

4 · Fetch

DB up Prisma loads places and events with their category and business relations. DB down The bundled Kosovo dataset is used instead. Both paths return the same PlaceDTO[] shape.

5 · Normalise

Coordinates are validated against Kosovo's bounding box. Anything missing or implausible is geocoded from the place name and address, then de-duplicated by slug. This is the location layer — it exists because map quality depends on it.

6 · Stream

HTML streams to the browser. Client Components (HeroSection, VibeSelector, ExploreSection) hydrate and take over.

7 · Client fetch

ExploreSection POSTs to /api/recommendations to fill the "Recommended for you" tab, because that depends on the mood and location held in the Zustand store — state the server does not have.

B. Saving a place (the feedback loop)

1 · Interaction

The heart button in PlaceCard toggles the id in the Zustand store immediately — the UI never waits for the network.

2 · Beacon

In parallel it fires navigator.sendBeacon("/api/interactions", …). A beacon survives the page being closed, which a normal fetch does not.

3 · Handler

src/app/api/interactions/route.ts applies a rate limit, validates the payload with Zod, and calls recordInteraction().

4 · Persist

interaction-service.ts writes a UserInteraction row with a type and weight. If the database is unavailable it logs and returns a prototype response — the save still "works" from the user's point of view.

5 · Learn

Next time /api/recommendations is called for that signed-in user, profile-engine.ts reads their recent interactions and builds a preference profile, which the ranking engine blends into its score.

C. Generating a day plan

POST /api/itinerary

Server vs client is a deliberate choice

Pages that only need data available at request time are Server Components — they ship no JavaScript. Pages that hold filter state, call the API, or render a map are Client Components. The split is the main reason the homepage carries only ~9.8 kB of page JavaScript.

Surfaces, radius and elevation

  • .surface — bordered panel, no shadow. The default grouping device.
  • .surface-raised — adds shadow-soft, lifting to shadow-lift on hover. Used for place cards.
  • .section-plain — a top hairline instead of a card, for editorial sections.
  • Radius: 0.75rem base. Pills are used only for status, never for navigation.
  • Shadows: three tokens only — soft, lift, overlay. Older names (glow, glass, pulse) still resolve, aliased to the calm values, so no markup broke during the redesign.

Motion

  • Durations between 180 ms and 450 ms, with one shared easing curve ease-calm — cubic-bezier(0.22, 1, 0.36, 1).
  • Hover effects are colour and elevation only. No 3D tilt, no shimmer, no looping animations.
  • A global prefers-reduced-motion block collapses every animation and transition to 0.01ms.
Why it changed

The earlier interface used glassmorphic panels, six shadow tokens, a 3D mouse-tilt on cards and a teal glow. It read as a SaaS dashboard. The current system uses warm stone tones, one accent, and a serif for editorial moments — closer to a travel guide than a control panel.

One Zustand store for everything the browser owns.

src/store/app-store.ts holds the state that is genuinely client-side — the things the server cannot know. It is persisted to localStorage under stay-kosovo-app-state.

10. Languages

Two locales, 391 keys each, kept in exact parity.

Resolution order

src/i18n/i18n-provider.tsx decides the active language in this order:

  1. localStorage / sessionStorage key stay-kosovo-language
  2. The browser's language, reduced to its base code (sq-AL → sq)
  3. English

The chosen language is written back to storage and applied to document.documentElement.lang.

Two kinds of string

Interface copy

Read with t("discover.title") from locales/en.json. Around 390 keys grouped by feature: hero, explore, mobility, and so on.

Domain labels

Data values like "Local Food" or "WALKING" come from the database, not the UI. useLocalizedLabels() maps them through a domain.* namespace so they still translate, falling back to the raw value. 

// src/i18n/use-localized-labels.ts
labels.vibe("Local Food")        // → "Something delicious"   (slugged lookup)
labels.transport("WALKING")      // → "Walk"                  (exact lookup)
labels.category("cafes")         // → "Cafe"
labels.availability("surging")   // → "Very busy"

Adding a language

  1. Copy src/i18n/locales/en.json to xx.json and translate the values — keep every key.
  2. Register it in src/i18n/client.ts under resources.
  3. Add the entry to languages[] in src/i18n/settings.ts.
  4. Run the key-parity check below; both files must report the same count.
node -e "const e=require('./src/i18n/locales/en.json'),s=require('./src/i18n/locales/xx.json');
const f=(o,p='')=>Object.entries(o).flatMap(([k,v])=>v&&typeof v==='object'&&!Array.isArray(v)?f(v,p?p+'.'+k:k):[p?p+'.'+k:k]);

NextAuth route handler signature

The auth handler is wrapped for rate limiting, so it must forward the App Router context: handler(req, context) where context.params resolves to { nextauth: string[] }. Passing undefined makes NextAuth fall back to its Pages-Router code path and read req.query, which does not exist on a Web Request — every /api/auth/* call then returns 500 and sign-in breaks completely. 12. Domain engines

Five deterministic functions that do the actual thinking.

11.1 Recommendation engine

src/services/recommendation-engine.ts

Takes an input object (moods, budget, city, coordinates, transport preference, day part, party size, avoid-crowds) and a candidate list, and returns scored results with a breakdown. Nothing is random — the same input always produces the same ranking, which is what makes it auditable and testable.

FactorWeightWhat it measures
Mood fit24%Overlap between requested moods and the place's mood tags.
Quality16%Rating and review volume.
Distance12%Haversine distance from the user, when a location is known.
Novelty12%The place's hidden-gem score — rewards the less obvious.
Budget10%Fit between price level and the stated budget.
Mobility10%Whether the preferred transport method actually works here.
Context6%Time of day, party size, and crowd avoidance.
Personalisation6%Alignment with the learned interaction profile.
Business boost4%Capped paid visibility. Deliberately the smallest factor.

Each result also carries human-readable reasons — "Good for Local Food", "Few visitors know it", "Easy to get to" — generated from whichever factors actually fired.

11.2 Profile engine

src/services/profile-engine.ts

Converts a list of UserInteraction rows into a preference profile: preferred moods, preferred cities, preferred categories, average budget, mobility bias and hidden-gem affinity. Interaction types carry different weights, so a save counts for more than a view. The result feeds the 6% personalisation term above.

11.3 Pulse engine

src/services/pulse-engine.ts

Produces the live picture of a city. For each candidate place it computes an intensity score:

intensity =
    popularityScore      × 0.32
  + hiddenGemScore       × 0.20
  + rating               × 8
  + eventHeat            × 0.22
  + transportReliability × 0.08
  + moodMatch            (+10 if the selected mood applies)
  + dayPartBoost         (+9 evening nightlife, +7 morning trails)
  → clamped to 1…99

The top six become activity zones. Results are cached in-process for 30 s keyed on city + mood + day part + coarse location, so a busy page does not recompute the same thing.

The same engine also derives crowdMode, popular moods, transport health and supply gaps — which is why the homepage "Tonight" block, the /pulse page and the itinerary rationale all agree with each other.

11.4 Itinerary engine

src/services/itinerary-engine.ts

The generation pipeline, in order:

  1. Rank candidates with the recommendation engine, using the requested mood and budget.
  2. Read live city context from the pulse engine.
  3. Select stops while diversifying categories — no three restaurants in a row.
  4. Calculate mobility between each consecutive pair.
  5. Assign start times, dwell time and travel time to build the timeline.
  6. Stretch dwell time to fill the requested duration, then cap total cost at the budget.
  7. Persist Itinerary + ordered ItineraryStop rows when signed in.

11.5 Mobility engine

src/services/mobility-engine.ts

Computes all five methods for a pair of coordinates in one pass:

Two gates, on purpose

Middleware runs in the Edge runtime and cannot reach the database, so it only trusts the signed JWT in the cookie. It is a redirect gate, not a security boundary. 15. Fallback architecture

The app runs with no database and no API keys. Here is exactly how.

The reachability probe

src/lib/database-availability.ts opens a raw TCP socket to the host and port in DATABASE_URL with a 250 ms timeout. It never asks Prisma, so a dead database cannot hang a request for the driver's default timeout. 

reachable    → cached for 60 s   (DB_REACHABLE_CACHE_MS)
unreachable  → cached for 10 s   (DB_UNAVAILABLE_CACHE_MS)
concurrent   → one shared in-flight promise, not N sockets

Why this is worth the complexity

A fresh clone runs with npm install && npm run dev and nothing else. A demo cannot fail in front of an audience because a container did not start. And every engine is forced to be a pure function of its inputs — which is exactly what makes them testable.

16. Logging & timing

Structured logs and per-step timing, with a guarantee that neither can break a request.

Logger

src/lib/logger.ts — pino writing JSON to stdout.

  • Redaction of authorization, cookie, body.password and body.token.
  • No worker thread. The stream writes directly to file descriptor 1. A worker-thread transport gets bundled by webpack, resolves its worker script to a path that does not exist, and then throws the worker has exited on every log call. That is a real failure mode this codebase has already hit — the comment in the file exists to stop it coming back.
  • Non-throwing. The destination's write is wrapped and the stream has an error listener, so a logging failure can never surface as an uncaught exception.

Timing

src/lib/performance.ts provides timeStep(name, fn) for individual operations and withApiTiming(route, handler) for whole handlers. In development the result is attached to the response as a standard header: 

Server-Timing: total;dur=142.3, db.places.findMany;dur=88.1, rec.rank;dur=12.4
X-Response-Time: 142.3ms

Slow steps over 100 ms and slow routes over 250 ms are logged as warnings. Thresholds are configurable through PERF_STEP_SLOW_MS and PERF_SLOW_MS. The event-loop monitor only starts when PERF_LOGS=1 is set explicitly — otherwise it floods a development console with noise from the compiler.

17. Security

Layered, and each layer is independent of the others.

ControlWhereWhat it does
Content Security Policy src/middleware.ts Nonce-based script-src. The nonce is generated per request and Next.js stamps it onto its own scripts. 'unsafe-eval' is added only when NODE_ENV !== "production", because webpack's dev bundle evaluates modules with eval(); without it the client bundle is blocked and nothing hydrates.
Transport & framing headers src/middleware.ts HSTS, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, X-Frame-Options: DENY.
Role authorisation src/lib/auth/permissions.ts requireRole([...]) returns a response on denial, before any service call.
Rate limiting src/lib/rate-limit.ts Fixed-window buckets. In-memory by default, Redis when REDIS_URL is set. Applied to login, registration, reviews, interactions, recommendations, itinerary, mobility, assistant, weather and uploads.
Input validation src/lib/validation.ts Every body and query string is Zod-parsed before it reaches a service. Rejections are 400s with a message, never a stack trace.
CSRF src/lib/csrf.ts A token is minted into the JWT and exposed on the session for state-changing calls.
Password storage src/lib/auth/options.ts bcrypt hashing; comparison is timed as its own step.
Log redaction src/lib/logger.ts Credentials and tokens are censored before they can reach stdout.
Safe redirects src/app/auth/login/page.tsx ?next= is parsed against the current origin; anything cross-origin collapses to /.
Coordinate sanity src/lib/geo.ts Places outside Kosovo's bounding box are rejected from the map rather than plotted in the sea.
Trusted proxy

getClientKey() only honours x-forwarded-for and x-real-ip when TRUSTED_PROXY=true or in production. In development it uses a constant key so local requests do not lock each other out.

20. How it all connects

One narrative that ties every subsystem together.

The whole system is a loop. Supply is created, discovery surfaces it, people act on it, those actions become signal, and signal changes what gets surfaced next. Everything else — auth, maps, languages, the design system — exists to support that loop.

The one-sentence version

A mood and a location go in, a ranked list of real places comes out; whatever the person then does with that list is recorded, and next time the list is better.

21. Extending it

Common next steps, and where each one lands.

Add a field to a place

  1. Add it to model Place in prisma/schema.prisma.
  2. Run npm run db:migrate -- --name add_field.
  3. Add it to PlaceDTO in src/types/index.ts.
  4. Map it in dbPlaceToDTO() in src/services/location-layer.ts.
  5. Add it to the fallback objects in src/data/kosovo-data.ts so the no-database path still type-checks.

Add a mood

  1. Add an entry to vibes[] in src/data/kosovo-data.ts.
  2. Add domain.vibes.<slug> and domain.vibeDescriptions.<slug> to both locale files.
  3. Add an icon mapping in vibe-selector.tsx and the fallback in explore-section.tsx.

Make the scores live

popularityScore, hiddenGemScore, heatScore and boostScore are currently stored values. A scheduled job that recomputes them from UserInteraction counts would close the loop completely: 

popularity = weighted interaction count over the last 30 days, normalised
hiddenGem  = high rating + low interaction volume
heat       = event proximity × expected attendance
boost      = paid, capped, and never more than the 4% weight

The engines already read these fields, so no ranking code would need to change.

Swap in a real model

assistant-engine.ts already has an OpenAI path; set OPENAI_API_KEY and it switches over. The ranking engine is deliberately left deterministic — a model can be layered on top to explain the result, but the ordering should stay auditable.

Move rate limiting to Redis

Set REDIS_URL. rate-limit.ts already delegates to rate-limit-redis.ts when it is present, so no code changes are needed for a multi-instance deployment.

Add a language

See section 10. The only real work is translation; the plumbing is four small edits.

Go to production

  1. Provision PostgreSQL and set DATABASE_URL, NEXTAUTH_URL, NEXTAUTH_SECRET.
  2. Run npx prisma migrate deploy.
  3. npm run build then npm run start — or docker compose up --build.
  4. Confirm /api/health reports databaseConfigured: true.
  5. Verify the production CSP no longer contains 'unsafe-eval'.
